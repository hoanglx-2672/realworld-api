01Kiến trúc Modular

Ứng dụng NestJS là một cây module. Mỗi module gom một nghiệp vụ: controller (nhận HTTP), service (xử lý), entity (bảng DB), DTO (kiểm dữ liệu vào). Module chỉ cho bên ngoài dùng những gì nó exports.

Cây module của dự án

AppModule                         src/app.module.ts — gốc
├─ ConfigModule (global)          đọc .env
├─ TypeOrmModule.forRootAsync     kết nối Postgres (1 lần)
├─ I18nModule                     đa ngôn ngữ en / vi
├─ UsersModule                    /api/users, /api/user
│   └─ imports AuthModule         để ký token khi login
├─ ArticlesModule                 /api/articles
│   └─ imports AuthModule         để guard kiểm token
└─ TagsModule                     /api/tags
AuthModule                        không có controller; chỉ cấu hình + exports JwtModule

Mỗi thư mục là một nghiệp vụ

File trong src/articles/Vai tròĐược phép làm gì

Vì sao tách như vậy?

Controller mỏng thì đổi giao thức (REST → GraphQL) không đụng tới nghiệp vụ. Service không biết HTTP nên dễ test. Mapper đứng giữa entity và response nên thêm cột vào DB không vô tình lộ ra API.

Bẫy đã gặp

Reviewer độc lập chỉ ra service đang trả về { article }, tức là đã biết hình dạng response HTTP. Cách chuẩn hơn: service trả ArticleView, controller tự bọc { article: ... }.

Bài tập 1.1: Vẽ lại cây module

Mở app.module.ts rồi lần theo từng imports. Tự trả lời: vì sao ArticlesModule phải import AuthModule? Thử xoá dòng import đó, chạy npm run start:dev và đọc lỗi Nest báo.

Đáp án: JwtAuthGuard cần JwtService. JwtService nằm trong JwtModule, và AuthModule export nó. Bỏ import thì Nest báo "Nest can't resolve dependencies of the JwtAuthGuard (?)".

02@Module() decorator

@Module() nhận một object có 4 khoá. Nest đọc chúng lúc khởi động để dựng DI container, tức là tự tạo và tiêm các instance cho bạn.

KhoáÝ nghĩaVí dụ trong dự án

@Module({
  imports: [
    JwtModule.registerAsync({
      inject: [ConfigService],                     // xin ConfigService từ DI
      useFactory: (config: ConfigService) => ({
        secret: requireSecret(config.get('JWT_SECRET')), // thiếu hoặc rỗng → app không chạy
        signOptions: { expiresIn: parseExpiresIn(config.get('JWT_EXPIRES_IN')) }, // rỗng → 7d, sai → dừng
      }),
    }),
  ],

})

Bẫy đã gặp

04Kết nối database với TypeORM + PostgreSQL

Ba lớp: DataSource (kết nối) → Entity (class ↔ bảng) → Repository (đọc/ghi). Cấu trúc bảng chỉ được thay đổi bằng migration.

Bước 1: Một cấu hình dùng cho hai nơi

src/database/typeorm.options.ts

export function typeOrmOptions(env: NodeJS.ProcessEnv): DataSourceOptions {
  return {
    type: 'postgres',
    host: env.DB_HOST ?? 'localhost',

Hai nơi dùng chung cấu hình này: app Nest (TypeOrmModule.forRootAsync trong app.module.ts) và TypeORM CLI (data-source.ts). Nhờ vậy hai bên không bao giờ trỏ vào hai DB khác nhau.

Bước 2: Entity và quan hệ

src/articles/article.entity.ts (rút gọn)

@Entity('articles')
@Index('IDX_articles_author_id', ['author'])    // Postgres không tự index khoá ngoại
export class Article extends BaseEntity {      // id, created_at, updated_at
  @Column({ unique: true }) slug: string;
  @Column({ type: 'text' }) body: string;

  @ManyToOne(() => User, (u) => u.articles, { nullable: false, onDelete: 'CASCADE' })
  @JoinColumn({ name: 'author_id' })               // cột DB snake_case
  author: Relation<User>;                           // Relation<> vì User cũng import Article

  @ManyToMany(() => Tag, (t) => t.articles)
  @JoinTable({ name: 'article_tags', joinColumn: { name: 'article_id' },
               inverseJoinColumn: { name: 'tag_id' } })
  tags: Relation<Tag>[];
}

@ManyToOne / @OneToManyNhiều bài → một tác giảCột articles.author_id
@ManyToMany + @JoinTableBài ↔ tag, user ↔ bài yêu thíchBảng nối article_tags, favorites

Bẫy đã gặp

• N+1: nếu tính favorited từng bài một, 20 bài sẽ thành 20 câu SQL. Dự án dùng 3 câu IN (...) gộp, nên luôn là 6 câu dù trang dài bao nhiêu (đã đo với DB_LOGGING=true).

• @UpdateDateColumn không tự cập nhật khi chỉ đổi tag, vì TypeORM chỉ ghi vào bảng nối, không UPDATE bảng articles. Phải tự đặt, và đặt bằng giờ của DB (CURRENT_TIMESTAMP, cùng nguồn với createdAt), không dùng new Date() của app: hai đồng hồ lệch nhau thì updatedAt có thể nhỏ hơn createdAt (ISS-27).

• Thiếu transaction (review tìm ra, đã sửa ở PR art-4): tag được tạo trước, sau đó lưu bài bị lỗi, thì tag bị mồ côi. Thêm nữa, PUT và DELETE gọi cùng lúc làm bài đã xoá "sống lại", vì save() không thấy dòng nên INSERT lại.

05Authentication với JWT

JWT là một chuỗi gồm header.payload.chữ_ký. Server ký bằng JWT_SECRET. Khi token quay lại, server chỉ cần kiểm chữ ký, không cần lưu phiên trong DB.

Toàn bộ luồng

1. Đăng ký / đăng nhập
POST /api/users/login  {"user":{"email","password"}}
  → bcrypt.compare(password, hash)        // không bao giờ lưu mật khẩu thô
  → jwt.signAsync({ sub: user.id })       // payload CHỈ có id
  ← {"user": {..., "token": "eyJhbGci..."}}

2. Gọi API cần đăng nhập
PUT /api/user   Authorization: Token eyJhbGci...   // spec dùng "Token", không phải "Bearer"
  → JwtAuthGuard: tách token → jwt.verifyAsync → request.auth = { userId }
  → @CurrentAuth() lấy request.auth ra cho controller

Đăng nhập: chống dò email

src/users/users.service.ts

const user = await this.users.createQueryBuilder('user')...getOne();

// Không có user vẫn so với một hash GIẢ → thời gian phản hồi như nhau,
// kẻ tấn công không đo được "email này có tồn tại".
const ok = await compare(dto.password, user?.password ?? DUMMY_HASH);
if (!user || !ok) {
  throw errorsException(401, 'credentials', 'errors.invalid'); // cùng 1 câu cho cả 2 trường hợp

Guard: người gác cổng

src/auth/jwt-auth.guard.ts

@Injectable()
export class JwtAuthGuard implements CanActivate {
  protected readonly optional: boolean = false;
  constructor(
    private readonly jwt: JwtService,
    @InjectRepository(User) private readonly users: Repository<User>, // AuthModule export
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest();
    const token = extractToken(request);    // undefined: không có header · null: sai dạng
    if (token === undefined) {
      if (this.optional) return true;           // khách được xem
      throw errorsException(401, 'token', 'errors.tokenMissing');
    }
    if (token === null) throw invalidToken();   // "Bearer x" → 401, không coi là khách
    const userId = await this.verify(token);    // sai chữ ký / hết hạn → undefined
    // token đúng chữ ký nhưng user đã bị xoá → cũng 401
    if (userId === undefined || !(await this.users.existsBy({ id: userId }))) {
      throw invalidToken();
    }
    request.auth = { userId, token };
    return true;
  }
}

// Endpoint công khai nhưng "biết" người xem (favorited, following):
export class OptionalJwtAuthGuard extends JwtAuthGuard {
  protected override readonly optional = true;
}

  @IsString()
  @MaxLength(255)
  @NoNulChar()     // ký tự \u0000 làm Postgres lỗi 500 (decorator tự viết)
  title: string;
}
export class CreateArticleRequestDto {
  @Wrapped(() => CreateArticleDto)   // {"article": {...}}: IsDefined+IsObject+ValidateNested+Type
  article: CreateArticleDto;
}

Nest còn có pipe dựng sẵn cho tham số đơn lẻ, ví dụ @Param('id', ParseIntPipe) id: number: "abc" sẽ thành lỗi 400.

Exception: ném lỗi đúng định dạng spec

src/common/http-errors.ts

export function errorsException(status: HttpStatus, field: string, key: string) {
  return new HttpException({ errors: { [field]: [t(key)] } }, status);
}
// Dùng: throw errorsException(HttpStatus.FORBIDDEN, 'article', 'errors.forbidden');
// → 403 {"errors":{"article":["forbidden"]}}   (?lang=vi → "không có quyền")

// Đổi lỗi DB sang lỗi nghiệp vụ: Postgres 23505 (trùng unique) → 409
const column = uniqueViolationColumn(error);   // 'email' | 'username' | 'slug' | undefined

Nest có sẵn NotFoundException, ForbiddenException, UnauthorizedException... Dự án dùng HttpException với body tự định nghĩa, vì spec đòi body dạng {"errors": {...}} chứ không phải {"statusCode","message"}.

Đã có: Exception Filter toàn cục (ISS-01), và vì sao cần

Code thật: all-exceptions.filter.ts, đăng ký bằng { provide: APP_FILTER, useClass: AllExceptionsFilter } trong app.module.ts (qua DI để tiêm được I18nService). Trước khi có nó, các lỗi mình chủ động ném đều đúng định dạng, nhưng lỗi không lường trước thì không:

POST /api/users  body: {bad json         → 400 {"statusCode":400,"message":"Unexpected token...","error":"Bad Request"}
Lỗi DB bất kỳ (ví dụ FK 23503)           → 500 {"statusCode":500,"message":"Internal server error"}

Giờ: JSON hỏng → 400 {"errors":{"body":["is malformed"]}}, route lạ → 404 {"errors":{"path":["not found"]}}, lỗi lạ → 500 câu chung + log kèm stack. Bẫy: lỗi JSON xảy ra ở body-parser, trước middleware i18n, nên filter phải tự chọn ngôn ngữ.

Bài tập 6.1: So sánh bản mẫu dưới đây với bản thật trong dự án

Bản thật ở all-exceptions.filter.ts khác bản mẫu ở 4 chỗ: tiêm I18nService, bảng FRAMEWORK_ERRORS, hàm localeOf dùng lại đúng các resolver của i18n, và đặt Cache-Control: no-store cho mọi lỗi. Tự giải thích vì sao cần từng chỗ (gợi ý: lỗi JSON hỏng xảy ra trước middleware).

Tạo src/common/all-exceptions.filter.ts

@Catch()                                      // không tham số = bắt MỌI lỗi
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse<Response>();

    if (exception instanceof HttpException) {
      const body = exception.getResponse();
      // Đã đúng dạng {"errors": ...} (do mình ném) → giữ nguyên
      if (typeof body === 'object' && 'errors' in body) {
        return res.status(exception.getStatus()).json(body);
      }
      // Lỗi của Nest/Express (JSON hỏng...) → bọc lại
      return res.status(exception.getStatus())
        .json({ errors: { body: [exception.message] } });
    }

    // Lỗi không lường trước: log đầy đủ, trả câu chung (không lộ chi tiết DB)
    this.logger.error(exception);
    res.status(500).json({ errors: { server: ['internal error'] } });
  }
}

Đăng ký trong app.setup.ts bằng app.useGlobalFilters(new AllExceptionsFilter()), để test e2e cũng chạy qua filter. Viết test trước: gửi JSON hỏng → mong đợi body.errors tồn tại.

Thử thêm: câu 'internal error' nên đi qua i18n (key errors.internal) như các câu lỗi khác.

Bài tập 6.2: Viết LoggerMiddleware (dự án đã có NoStoreMiddleware làm mẫu)

Xem middleware thật đầu tiên: no-store.middleware.ts và cách đăng ký trong AppModule.configure(). Rồi tự viết thêm LoggerMiddleware:

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  private readonly logger = new Logger('HTTP');
  use(req: Request, res: Response, next: NextFunction) {
    const start = Date.now();
    res.on('finish', () =>
      this.logger.log(`${req.method} ${req.originalUrl} ${res.statusCode} ${Date.now() - start}ms`));
    next();                       // QUÊN next() → request treo mãi
  }
}

// app.module.ts: middleware đăng ký bằng configure(), không phải trong @Module()
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(LoggerMiddleware).forRoutes('*');
  }
}

Câu hỏi: vì sao không nên log req.body? (gợi ý: body login chứa mật khẩu.) Vì sao kiểm token đặt ở Guard mà không đặt ở Middleware? (gợi ý: middleware không biết route nào là tuỳ chọn.)

Bẫy đã gặp

• @IsOptional() cho qua cả null, nên {"tagList": null} lọt vào service. Dự án dùng ValidateIf(v => v !== undefined): chỉ bỏ qua khi field không gửi.

• Một field sai nhiều luật thì chỉ trả lỗi gốc. Ví dụ title rỗng chỉ báo "can't be blank", không kèm "is too long". Xem ROOT_CONSTRAINTS trong validation-exception.factory.ts.

• ?offset=1e20: Number.isInteger(1e20) là true, nên số khổng lồ lọt qua và Postgres trả 500. Cần chặn trên bằng @Max().
